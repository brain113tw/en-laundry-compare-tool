# 前端安全檢視與補強紀錄｜v5.9

## 範圍

以使用者提供的 `en_compare_manager_v5_8.html` 為基礎，靜態核對程式並在交付的 `index.html` 加入補強；再進行有限的瀏覽器回歸測試。**沒有掃描或更動 laundry.com.tw、GitHub 帳號設定或目前線上的 Pages。**

v5.8 基線 SHA-256：`1d845ba697bf384bb6f246be6de6fe518fc834fb18154774909f03023e7d2f1a`。

目前版本 `index.html` SHA-256：`cdbe5b84305db121f5ba7549b27cddfa94683aabacb49b886b5c3525772b2e4b`。

## 原始程式中可核對的內容

基線已有 CSP、以 Blob／Canvas 在本機處理圖片、輸出 MIME 核對、圖片數量／單檔容量／輸出像素限制、動態檔名以 textContent 顯示等措施。

原始設定匯入主要檢查 `cfg` 是否為 object，並把它直接展開到 defaults；慣用版型也直接合併設定。這不足以確保數值有限、型別正確或結構大小合理。本次**未把此問題定性為已證實的遠端程式執行漏洞**；主要可直接確認的是異常狀態、資源耗用和錯誤處理風險。

另外，`script-src 'unsafe-inline'` 允許更多內嵌腳本；資料夾計數沒有一致的跨根目錄預算；讀取 localStorage 的內容缺少完整欄位驗證。

## 本次已落地的補強

### JSON 輸入

所有設定檔、慣用版型檔和 localStorage 內容共用 bounded parser。檔案在 `.text()` 前先檢查大小（非空白、最多 1 MiB），解析後限制 12 層、4096 節點及單一物件／陣列 256 個項目。JSON 全樹的 `__proto__`、`constructor`、`prototype` 鍵直接拒絕。

cfg 只複製 defaults 的已知欄位。數值需是有限 number；布林需是 boolean；選單需是允許值；色碼限定 #RRGGBB；文字限制長度。超界有限數值做範圍限制並記錄，型別錯誤則拒絕整筆。固定輸出超過 2000 萬像素時拒絕套用；依原圖計算的尺寸還會在渲染時檢查。

慣用版型最多 12 組，拒絕重複名稱與壞項目。全部檢查通過後才替換；已有版型時先確認。匯入失敗保留既有狀態。localStorage 讀寫失敗會顯示「僅暫存」而不是假裝永久儲存。

### CSP 與外部連線

主頁 `script-src` 使用 SHA-256 白名單、`script-src-attr 'none'`；保留 `default-src 'none'`、`connect-src 'none'`、`object-src 'none'`、`base-uri 'none'`、`form-action 'none'`，並明確禁止 worker／media 資源。frame 原本也是禁止的；v6.2 加入 HEIC 解碼後改為只允許同站（`frame-src 'self'`），原因與驗證見下方「HEIC 解碼元件」。圖片只允許 data:／blob:。沒有加入外部 JavaScript、字型、計數徽章或分析碼。

額外內嵌 script 阻擋與對外 fetch 拒絕有測試記錄。`connect-src` 不是「封鎖一切網路」：初次載入線上網站和使用者點連結仍會導覽到外部網站。外連使用 noopener／noreferrer，頁面 referrer policy 為 no-referrer。

**仍保留 CSS 的 `style-src 'unsafe-inline'`**，因工具原有大量 inline style 及動態樣式。沒有將此包稱為全面 strict CSP。SHA-256 不能防止已有寫入權的攻擊者連程式和 hash 一起改；它不是程式碼保密或簽章認證。

依 W3C 的 CSP 規則，meta 傳送不支援 `frame-ancestors` 等全部指令；本包沒有用無效 meta 設定宣稱防止點擊劫持。要新增這類防護須由可控制 HTTP response header 的部署層處理。[CSP Level 3](https://www.w3.org/TR/CSP3/)

### 圖片與資源限制

新增檔頭與副檔名相符檢查，拒絕偽裝成 JPG 的 SVG／HTML。單次掃描最多 1000 項（含目錄）和 16 層。保留 256 張、單張 50 MiB／6000 萬像素上限，新增來源總容量 256 MiB及已載入總像素 1.2 億；單張解碼等待設 15 秒期限。

**檔頭比對不是防毒或完整解碼驗證**。像素是在瀏覽器載入圖片後檢查，不能保證避免解碼器在檢查前分配記憶體，也不能以 setTimeout 中止所有同步解碼工作。仍需更新瀏覽器並避免不明輸入；資源上限不代表低配裝置一定流暢。

### DOM、操作與資料邊界

檔名、狀態、版型名稱走 textContent；標題是 Canvas 文字，不作 HTML 插入。本次對惡意樣式名稱與偽裝圖檔測試未觸發注入。

修正文字與底條命中層級、小數與滑鼠滾輪錯誤；清空照片時同步清空會引用已釋放 Blob 的歷史。批次檔名以不分大小寫比對避免 Windows 解壓混淆。相容舊入口改成導向主程式，避免 root 同時維護舊的可執行版本。

## v6.2 新增：專案檔、觸控縮放與 HEIC

### 專案檔是新的不受信任輸入

「開啟專案檔」讀入的 `.enproj` 可能來自別人，全部內容都當成不可信資料處理：

- 只接受不壓縮（stored）的 ZIP。壓縮、加密、使用 data descriptor、分卷的檔案一律拒絕；不做解壓縮，因此沒有解壓縮炸彈的問題。
- 先檢查整體大小（約 288 MiB）、項目數（300）、目錄大小（1 MiB），每個項目的位置與長度都必須落在檔案資料區內、彼此不可重疊，並驗證 CRC-32。禁止重疊是為了讓照片合計大小不可能超過檔案本身：否則 1 MiB 的檔案可以用 256 筆目錄指向同一段資料，展開成 256 MiB。
- `project.json` 上限 16 MiB，用同一個有界解析器檢查節點數、深度、單一物件大小，並拒絕 `__proto__`／`constructor`／`prototype` 鍵。
- 輸出檔名、批次格式與檔名前綴是後來加入的選填欄位：檔名與前綴必須是文字，去除控制字元後截到 100／40 字；格式不在允許清單內就改用預設值。
- 欄位逐項白名單：對比設定走原有的 `sanitizeConfig`，工具箱設定走 `validConfig`，位置、裁切、遮蔽、標記只接受有限數值並夾限到合法範圍，類型與顏色必須是允許值，照片只能引用清單內的編號。文字欄位會正規化為合法的 UTF-16（不成對的代理字元以 U+FFFD 取代），確保之後能再寫入檔名與專案檔。「輸出總像素超過 2000 萬」不再是拒絕理由：這是使用者在畫面上也能留下的狀態，專案檔如實還原，限制仍由繪製前的尺寸檢查執行，不會配置超限的畫布。
- ZIP 內的項目名稱不採信：照片項目名稱由序號與副檔名推導，副檔名必須在允許清單內；檔名中的路徑分隔與控制字元會被移除。
- 照片位元組仍走原本的匯入流程（檔頭簽章、單張與合計容量、像素上限、瀏覽器解碼），但先解碼到暫存清單，不動目前的工作階段。照片與編號的對應以清單位置為準；路徑、大小、日期完全相同的重複項目整份拒絕。
- 結構驗證通過後先詢問；照片解碼完成、至少一張能顯示才取代目前的工作階段。任何一項驗證失敗，或沒有任何照片能顯示，就整份拒絕，目前的照片與編輯不變。部分照片無法解碼時先說明張數並再次詢問；接受後略過那些照片，並丟棄引用它們的指定、批次組合與工具箱編輯。
- 載入期間兩個工作區都保持鎖定，舊清單不能被操作。
- 存檔前會用同一套驗證自我檢查，避免寫出這個版本自己打不開的檔案。

專案檔內含原始照片與檔名、相對路徑，等同客戶資料；文件已提醒不要上傳公開 repo。

### 第二輪審查修正的隱私問題

- 輸出尺寸超過限制時，舊版的裁切／遮蔽頁會停在先前的畫面，但滑鼠操作仍以新照片的座標生效，一次拖曳就可能把既有遮蔽框移到別處而畫面沒有變化。現在這兩頁與「查看原圖」一律以原圖繪製、以原圖座標計算；成品預覽無法繪製時清空畫面並停止接受拖曳與方向鍵。
- 馬賽克原本以一般疊加方式畫回去，來源有透明像素時，原本的不透明像素（例如透明底上的文字）會原樣透出。現在馬賽克與模糊都先鋪不透明底色。
- 馬賽克格子與模糊半徑的下限原本以「正在繪製的畫布像素」計算，預覽較小時看起來比輸出粗。現在下限以原圖像素定義（不細於編輯畫面的兩個像素），輸出不會比畫面顯示的更細。
- 新畫的遮蔽框不再保持選取，「遮蔽方式」不會把剛畫好的實色框改成模糊；選取的對象會寫在面板上。
- 全尺寸輸出時每處理一個模糊／馬賽克遮蔽就讓出執行緒並檢查停止鈕，40 個全幅模糊不再把分頁卡住到無法停止。

### HEIC 解碼元件：第三方程式碼與它的隔離

Safari 17 以上能自己解碼 HEIC，其他瀏覽器不能。為了讓 Chrome、Edge 也能開 iPhone 的照片，本版加入第三方解碼器 libheif-js 1.23.5（libheif 與 libde265 的 WebAssembly 版，LGPL-3.0）。這改變了「沒有第三方程式碼」的前提，所以用下面的方式限制它能做的事。

放在哪裡：解碼器不在 `index.html` 裡。它在另一個檔案 `vendor/heic-decoder.html`，以不會執行的文字區塊原樣收錄；同一頁的膠合程式（原始碼 `tools/heic_decoder_glue.js`）把它放進背景執行緒執行。`node tools/build_heic_decoder.mjs --check` 核對收錄的檔案是否就是 npm 上 libheif-js 1.23.5 的 `libheif-wasm/libheif-bundle.js`（SHA-256 `074b2b55ef3de477ba9f794ca381f3f0324c1cba8c91b4af07395f39c22d54cc`）。

主程式的 CSP 只改了一項：`frame-src 'none'` 變成 `frame-src 'self'`。`script-src` 仍然只有兩個內嵌腳本的 SHA-256，沒有加入 `'wasm-unsafe-eval'`，`connect-src`、`worker-src`、`object-src` 仍是 `'none'`。主程式本身不執行任何第三方程式碼。

怎麼隔離：

- 主程式只在加入 HEIC 而瀏覽器無法顯示時，才建立 `<iframe sandbox="allow-scripts">` 載入解碼頁。沙箱沒有 `allow-same-origin`，頁面的來源是不透明的：讀不到主程式的 DOM 與變數、`localStorage`、cookie、IndexedDB，不能開新視窗，也不能把上層頁面導向別處。
- 解碼頁有自己的 CSP：`default-src 'none'; script-src '<膠合程式的雜湊>' 'wasm-unsafe-eval'; worker-src blob:; base-uri 'none'; form-action 'none'`。沒有任何連線、圖片或其他腳本的許可；`'wasm-unsafe-eval'` 只允許編譯 WebAssembly，不允許 `eval`。背景執行緒繼承同一份政策。
- 兩邊只用訊息溝通：主程式送出一張照片的位元組，解碼頁回傳寬、高與像素。主程式只接受來自那個框架視窗的訊息，並把回覆當成不可信資料檢查：寬高必須是正整數、不超過 6000 萬像素，像素緩衝區的長度必須剛好等於寬 × 高 × 4。不合就丟棄這張並關掉框架。
- 解碼器在配置像素之前先檢查尺寸，超過上限直接拒絕。每張有 180 秒期限。任何一張失敗後框架整個丟棄，下一張用新的；匯入結束後框架也會移除。
- 框架只能載入同站的頁面：它自己想跳到別的網站會被主程式的 `frame-src 'self'` 擋下。

在 Chromium 實測的項目（`tests/check_heic.py`）：實際的解碼頁與它的背景執行緒都無法 `fetch`、載入圖片或腳本、開 WebSocket、執行 `eval` 或插入內嵌腳本，也讀不到上層頁面與儲存空間；測試期間另一個網站沒有收到任何請求。把解碼頁換成惡意頁面時，它同樣碰不到工具、儲存空間、cookie、IndexedDB、彈出視窗與上層導覽，也讀不到工具的檔案，想跳到別的網站會被擋下。會說謊的解碼頁（尺寸不合、缺像素、型別錯誤、負數、回覆別人的請求、回報當機）每一種都被拒絕或忽略，只損失正在處理的那一張。不是來自框架的訊息一律忽略。

仍然存在的風險：

- 現在隨工具散布約 2 MB 的第三方程式碼。它來自 npm 的預先編譯檔，以 SHA-256 固定版本，但本專案沒有自行從原始碼編譯，也沒有審查它的內容。
- 解碼器若有漏洞，惡意的 HEIC 最多能讓那一張照片解出錯誤的畫面，或讓解碼失敗、變慢。依上面的隔離，它拿不到其他照片，也無法把資料送出去。這個結論依賴瀏覽器的沙箱、CSP 與 WebAssembly 隔離正確運作，且只在 Chromium 實測過。
- `frame-src 'self'` 表示框架內的頁面可以改載入同一個網站上的其他頁面。這不會把資料送到第三方，但如果同一個網站上還放了別的不可信內容，隔離就取決於那些內容。請不要把工具和不可信的網頁放在同一個網域。
- 主機若以標頭禁止內嵌（`X-Frame-Options: DENY`、`frame-ancestors 'none'`），解碼頁會被擋下，HEIC 退回提示；這是功能失效，不是安全問題。

色彩與畫質：解碼後的像素若宣告為 Display P3（ICC 描述檔或 nclx），在解碼頁內換算成 sRGB 再回傳；兩者都有時以 ICC 為準。其他色彩空間不換算，操作紀錄會註明。不透明的照片暫存成品質 1、色度不抽樣的 JPEG，有透明的暫存成 PNG；原始的 HEIC 位元組仍保留給專案檔。

### 載入照片的總量上限

載入的照片在瀏覽器裡會保持解碼狀態，最多約每像素 4 位元組，直到瀏覽器需要回收記憶體。合計上限原本一律是 1.2 億像素。本版在瀏覽器回報記憶體 8 GB 以上、且不是行動裝置時（電腦版 Chrome／Edge）放寬為 2.4 億像素；其他情況不變。依據是實測：在 Chromium 載入 2.44 億像素的 HEIC 照片，瀏覽器各程序合計約 2.5 GB，模擬記憶體不足時會釋放一部分且工具仍可輸出。Safari、Firefox、手機與平板沒有量測，維持原本的上限。

### 其他

- 關閉分頁前的提醒（`beforeunload`）只是提醒，不會保存任何資料，也不寫入瀏覽器儲存空間。它按工作項目各自判斷（對比圖、每組批次、工具箱每張照片），輸出其中一項不會讓其他項目失去提醒。
- 雙指縮放只改變目前照片的縮放與位置，數值與滑鼠滾輪使用相同的夾限。
- 本段新增的程式沒有新增任何 HTML 字串插入、外部連線或瀏覽器儲存空間的使用。唯一新增的子資源是上面說明的同站解碼頁。

### 這一段的驗證限制

HEIC 的瀏覽器原生解碼（Safari）無法在測試環境驗證。隨附解碼元件的解碼結果與隔離只在 Chromium 驗證，沒有在 Firefox、Safari 或 Windows 上執行；解碼正確性以合成樣本，以及另一套測試集的 50 個檔案（含真實手機與相機的照片，未收錄在 repo）對照參考解碼器。觸控手勢以 Chromium 的觸控輸入驗證，未在實體手機或平板上測試。專案檔以 Chromium 驗證存取往返、25 種損毀或惡意內容的拒絕，以及全部或部分照片無法解碼時的處理。隱私遮蔽的修正以合成圖片逐像素驗證，沒有用真實證件或個資樣本測試。

## 仍存在的限制

純前端程式會被使用者取得；不能在裡面放 Token 或商業機密。localStorage 是 origin 級、未加密的瀏覽器資料，不是安全保險箱；檔名、標題和 ZIP 清單也可能含客資。瀏覽器擴充套件、裝置感染、主機／帳號遭接管、跨 origin 儲存差異、影像解碼漏洞不屬於這次可全面排除的範圍。

照片與批次編輯沒有跨工作階段保存。也沒有把「平台縮圖預覽」當成 FB／IG 的真實即時呈現。[localStorage 的官方瀏覽器說明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

## 驗證結論

本次 43 項指定檢查通過，包含 JSON、拖移、三格式編碼、ZIP CRC、文字安全輸出及 CSP 行為；這是限定測試樣本的結果，**不是「沒有漏洞」的保證**。v5.9 當時的測試採 Linux Chromium 144 headless（目前版本的測試環境與項數見 [測試紀錄](TEST_RESULTS.md)），使用完整 HTML 的 set_content；Windows file://／線上 Pages、持久儲存、下載落盤與其他瀏覽器尚需實機確認。
